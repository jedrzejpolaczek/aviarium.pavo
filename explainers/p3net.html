P3Net - P3 + a surrogate for neural architecture search

How P3Net actually works

This document assumes you already know pure P3 - the pyramid, hill climbing, the linkage tree, the crossover sweep. P3Net adds exactly one new idea on top of that: a cheap, learned stand-in for a real evaluation inside crossover - plus everything that had to be built to make that stand-in safe to use.

The same layout as the P3 document: context, then the big moving parts, then each one broken down in detail, then a live simulation, code, and finally a comparison.

1Context - the problem P3Net answers

In one sentence: pure P3 assumes evaluation is cheap. In neural architecture search (NAS), one evaluation means training a neural network - and that assumption simply isn't true.

In pure P3, crossing one candidate with one pyramid level spends one real evaluation per cluster in the sweep - for a genotype with a dozen or more linkage clusters, one such event is a dozen to several dozen evaluations at once. On a bit string, where evaluation takes milliseconds, that's a negligible cost. When evaluation means training a network for minutes or hours, that same cost can dominate the entire compute budget before the pyramid manages to grow even one level.

There's also a second change, unrelated to cost: network architectures are usually evaluated two ways at once - quality (validation error) and compute cost (parameters or FLOPs). P3Net therefore has to define what “improvement” means when improvement is no longer a single number.

What exactly doesn't change

The pyramid, hill climbing (FIHC), a linkage tree built by UPGMA over measured statistical dependence, the crossover sweep from smallest cluster first, no separate mutation operator - P3Net inherits all of this from pure P3 unchanged. If any of these terms is unclear, the P3 document explains each one from the ground up, live simulation included.

2Big picture - one P3Net iteration

Intuitively: take a parent you actually know, try to improve it cheaply and tentatively in as many ways as possible, and pay for a real evaluation only once - at the end, on the one candidate that survived the whole attempt.

3Components - four things P3Net adds to P3

The pyramid, hill climbing, and the linkage tree are described in the P3 document and don't return here. Below are only the four parts that pure P3 doesn't have.

3.1Genotype and two objectives at once

Intuitively: the genotype is a list of network design decisions (which operation on each cell edge, plus discretized training hyperparameters), and every genotype is evaluated two independent ways - how well the network performs, and how much it costs to compute.

A note on sign: the paper minimizes f₁ as an error. This document and the live simulation below flip the sign and maximize “quality” instead - a purely cosmetic swap to avoid a min/max tangle in the code; the mechanics (relative surrogate, sweep, non-dominated selection) are identical.

3.2The surrogate δ̂F - relative, linkage-aware

Intuitively: instead of learning to guess network quality from scratch from the raw encoded genotype, the surrogate learns something much narrower and easier: how much quality will change if I change only these specific few genes that happen to differ between the candidate and a parent whose quality I already know.

The training data for δ̂F comes exclusively from H_t - the set of all genuinely evaluated solutions collected so far: for every pair of observations differing on the same subset of loci F, the difference in their real f₁ values is one training example. The more real evaluations, the more such pairs, the better the surrogate - this is exactly the “retrain δ̂F” in the loop diagram in section 2.

3.3The tentative-acceptance chain and depth κ

Intuitively: one tentative, surrogate-based step is a small, manageable risk. Ten such steps in a row, stacked on each other with no real check at all - that's a prediction error that can accumulate in an unknown direction. κ is a hard limit on how many such steps are allowed to stack up before a real evaluation resets the error to zero.

3.4Selecting C* and the real evaluation

Intuitively: when only one number counts, “better” simply means bigger. When two numbers count at once - error and cost - a candidate only qualifies as an improvement if it's no worse in either dimension and better in at least one. That's Pareto non-domination, and it, not a plain > comparison, now decides promotion to a higher pyramid level.

Selecting non-dominated candidates is scoped to one iteration: only results produced against the same snapshot of H_t, with the same, not-yet-retrained surrogate, are compared. This keeps the comparison fair - estimates from before and after retraining δ̂F, which could drift in different directions, are never mixed.

4  See it in action

Not an animation of one fixed example - this is the algorithm actually running, exactly per the pseudocode in section 5, computing in your browser. Real neural networks can't be trained in a browser, so below is a toy but honestly computed NAS problem, in the same style the paper describes.

4.1The problem: a small, deceptive cell to design

The genotype below has 6 loci: 5 cell edges (each choosing an operation ∈ {conv, skip, none}) and one discretized hyperparameter - a learning-rate bucket (∈ {low, medium, high}). This is exactly the genotype shape from section 3.1: Λ₁×⋯×Λ₅×Θ.

Invalidity g(x): if all 5 edges are none, there's no path at all from input to output - such a genotype is rejected before any scoring.

Cost f₂ (always free, computed analytically): in this toy example it depends only on the learning rate - low = 0 (a safe, short schedule), medium = 1, high = 2 (the most expensive warm-up schedule). It deliberately does not depend on the choice of edge operations - this way, a quality improvement from discovering the {conv, conv} cluster isn't automatically punished with a higher cost, and the sweep can genuinely demonstrate the full P3Net mechanism with real pyramid promotions. Range: 0–2, less = cheaper.

4.2The solution: P3Net actually run on this cell

The same genotype from 4.1 is now going through a genuinely running P3Net, exactly as described in sections 2–3 and the pseudocode in section 5: pyramid and hill climbing unchanged, crossover scores every step with the surrogate δ̂F instead of training a network, chain depth is bounded by κ, and a real evaluation lands only once per sweep.

The surrogate below is a genuinely trained, though deliberately simple, model: for every subset F the linkage tree has already discovered, it remembers the average observed quality change for a specific value substitution on that subset, updating with every new real evaluation - nothing here is hardcoded or scripted.

5  Pseudocode - what exactly changes relative to P3

Four procedures; two of them (hill climbing, linkage-tree construction) are literally the same as pure P3 and aren't repeated here - see the P3 pseudocode.

procedure ITERATE-P3NET
    x ← random solution
    x ← HILL-CLIMB(x)                       // unchanged - P3 pseudocode
    if g(x) > 0 then continue              // §3.1: invalid, reject before anything
    if x ∉ seen then
        H.add(x, f1(x), f2(x)); P[0].add(x); seen.add(x)

    i ← 0
    while i < len(pyramid) do
        x' ← OPTIMAL-MIXING-SWEEP(x, P[i])  // §3.2–3.3: surrogate + kappa, not one evaluation per step
        f1', f2' ← EVALUATE(x')             // the only real evaluation in this sweep
        H.add(x', f1', f2')
        RETRAIN(δ̂); REBUILD-TREE(P[i])       // §2: before the next parent's sweep runs
        if DOMINATES(f1', f2', x) and x' ∉ seen then
            x ← x'
            P[i+1].add(x); seen.add(x)      // creates a new level if i+1 didn't exist yet
            i ← i + 1
        else
            break                       // stops climbing, settles at level i
procedure OPTIMAL-MIXING-SWEEP(x, Pi)
    tree ← BUILD-LINKAGE-TREE(Pi)           // unchanged - P3 pseudocode
    chain ← 0
    for F in tree do                       // smallest subset first
        if chain ≥ κ then break              // §3.3: hard chain-depth limit
        d ← random solution in Pi where d differs from x on F
        x' ← x with x'[F] = d[F]              // propose, tentatively - §3.2
        if δ̂(x, x', F) ≥ 0 then
            x ← x'                          // tentative acceptance - WITHOUT a real evaluation
            chain ← chain + 1
        // rejected or not: the sweep moves to the next F anyway
    return x
function δ̂(x, x', F)
    key ← (F, x[F], x'[F])                  // exact value substitution on this subset
    if key in table then return table[key]     // §3.2: average observed difference FOR THIS substitution
    if F in table_F then return table_F[F]  // fallback: average for the whole subset F
    return 0                          // no data - don't reject up front, no evidence against it

procedure RETRAIN(δ̂)
    table ← {}; table_F ← {}
    for (a, f1_a), (b, f1_b) in pairs(H) where a, b differ on the same F do
        table[(F, a[F], b[F])] ← average(f1_b − f1_a)   // §3.2: relative, not absolute
        table_F[F] ← average(f1_b − f1_a)
function DOMINATES(f1', f2', x)
    return f1' ≥ f1(x) and f2' ≤ f2(x) and (f1', f2') ≠ (f1(x), f2(x))  // §3.4: non-domination, not a plain >

That's the whole change. HILL-CLIMB and BUILD-LINKAGE-TREE from the P3 document return with not one letter different - P3Net adds exactly one new limit (κ), one new function (δ̂), and one new comparison rule (DOMINATES).

6  What P3Net adds - and what you still have to decide

All the decision points from the P3 checklist (genotype, fitness, invalid genotypes) still apply unchanged. Below are only the new ones that come with the surrogate.

Decision pointFixed by P3NetYou decide, per problem
Two objectives at once Promotion requires Pareto non-domination (f₁, f₂) against the parent, not a plain improvement of one number. What exactly f₂ is (parameters? FLOPs? inference time?), and whether it's genuinely free or just cheap.
Surrogate δ̂F Relative, linkage-aware, trained exclusively on pairs from H_t; acceptance threshold 0 by default. What class of model to use - this document and the live simulation deliberately use the simplest possible one: a table of averaged observations. Nothing stops you from replacing it with linear regression or a small network, as long as it stays relative and linkage-aware.
Chain depth κ Default κ = 2⌈log₂ n⌉ - a heuristic inherited from eLyMPuS, not a mathematical derivation for this application. Whether this value makes sense for your problem. Too small κ wastes the surrogate's potential (too-frequent real evaluations); too large risks compounded prediction error.
Cost of one evaluation Not addressed - this exact number decides whether P3Net makes sense at all relative to pure P3. If one evaluation is cheap, the whole extra surrogate mechanism is unnecessary complexity - go back to pure P3.
One thing P3Net is honest about

eLyMPuS guarantees discovering a missing dependency within 2⌈log₂ n⌉ steps - but that guarantee rests on an assumption of fitness-landscape monotonicity, which for neural network accuracy simply doesn't have to be true. δ̂F in P3Net is therefore treated as a learned heuristic estimator, without that guarantee - its quality is checked empirically (surrogate-quality analysis in the paper's results), not assumed up front.

Similarly, selecting non-dominated candidates in step 4 is scoped to one iteration - only results produced against the same snapshot of H_t, with the same, not-yet-updated surrogate, are compared, so that estimates from before and after retraining are never mixed.

✓Checklist for applying P3Net to a new problem

  • Do the pure P3 checklist first - genotype, fitness, invalid genotypes.
  • Check whether one real evaluation is expensive enough to justify a surrogate - if not, P3Net is unnecessary complexity.
  • Define the second objective f₂, if you have one, and make sure it can be computed without a full evaluation.
  • Choose a model class for δ̂F - start with something as simple as an averaging table, like the live simulation above, before reaching for anything more complex.
  • Set the chain depth κ and acceptance threshold (0 by default) - and check their sensitivity on your problem empirically, as the paper's Results section does.
  • Decide how often to retrain δ̂F and rebuild the linkage tree - after every real evaluation, as here, or less often.
P3Net: P3 (Goldman and Punch, GECCO 2014) extended with a relative, linkage-aware surrogate δ̂F, inspired by eLyMPuS/LyMPuS - applied to multi-objective neural architecture search (NAS).
