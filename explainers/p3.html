P3 - Parameter-less Population Pyramid

How P3 actually works

Not P3Net - the original algorithm it builds on. From the one idea it's built around, through the four procedures you need to write to implement it, to the handful of decisions you still have to make yourself every time you apply it to a new problem.

Laid out like a C4 diagram: context, then the big moving parts, then each one broken down in detail, then code, and finally a practical checklist.

1Context - the problem P3 answers

In one sentence: a classic genetic algorithm makes you guess two numbers up front - population size and generation count. P3 makes you guess neither.

These aren't cosmetic details. A poorly chosen population size makes a GA either waste evaluations maintaining diversity it doesn't need, or converge prematurely because it never had enough diversity to find the answer. Tuning it usually means running the same problem repeatedly at different sizes - which defeats the point of using a black-box optimizer on an expensive problem in the first place. P3 (Goldman and Punch, GECCO 2014) removes both parameters: size emerges from how hard the problem turns out to be, and the algorithm stops itself once it stops making progress.

P3 gets this for free by combining three ideas, each old on its own - hill climbing, hierarchical populations, and linkage-aware recombination - in a specific arrangement where each one covers the others' blind spot. That arrangement is the whole algorithm, and the rest of this page breaks exactly that down: section 2 shows it as a single loop (exactly the one on the right above, just in full detail), and section 3 opens each of its parts individually.

2Big picture - three parts, one loop

In one sentence: P3 has exactly three moving parts that one new solution passes through each iteration. Everything else is bookkeeping around them.

PartJob
Hill climberTakes a freshly created solution and drags it to a local optimum before it even joins any population.
PyramidA stack of populations of growing size. A solution advances one level at a time; nothing is ever discarded.
Linkage tree + crossoverFor each level, learns which genes tend to move together, then recombines using those groups instead of guessing.

3  Components - breaking each part down

The same three parts as above, now at the level of detail needed to implement them.

3.1Hill climber - first-improvement climbing (FIHC)

In one sentence: check genes one by one in random order, take the first improvement you find, and repeat the whole sweep until no change helps anymore.

Visit every gene position in random order. At each one, try every other allowed value it can take. The moment one is a strict improvement, take it immediately - don't check the other options for that gene, don't check the rest of the genome looking for a better move. Keep sweeping until a full pass changes nothing.

“First improvement” (as opposed to “steepest ascent,” which evaluates every neighbor before picking the best one) is why this has O(N) complexity per pass instead of O(N²) - for N genes it costs at most N+1 evaluations to fully solve a linear function. There's also no positional bias, since the gene visiting order is re-randomized every time.

3.2Pyramid - levels, uniqueness, and where “population size” comes from

In one sentence: a level only grows when something actually beats it - nobody sets its size up front.

Each level Pi holds a set of solutions. Each level's contents are disjoint from every other level's - a single global hash set enforces that no solution ever appears twice anywhere in the pyramid, checked in constant time. A solution's level is one higher than the level it last managed to improve against.

This is the whole trick behind not choosing a population size: a level only grows as long as it keeps producing improvements as climbers pass through it. Once solutions stop being able to climb past it, it simply stops growing - nothing forces it to a target size, and nothing caps it either.

3.3Linkage tree - learning which genes belong together

In one sentence: count how often pairs of genes change value together, and merge into one cluster the pairs that do so most often.

Each level keeps a table of how often every pair of gene positions takes every pair of values, updated every time a solution joins that level. From this table P3 builds a tree, repeatedly merging the two gene clusters whose values best predict each other - measured as the joint cluster's entropy against the sum of the two separate entropies. Two nearly redundant clusters (knowing one tells you the other almost for free) merge early; two that change independently merge late, close to the root.

Before the tree below is built, this looks like an ordinary count table - an example for 50 solutions on one level:

The less often a pair shows up in the “0,1” and “1,0” columns relative to “both 0” and “both 1,” the smaller the distance D - these two genes almost always change value together. The same three pairs and the same D values come back in the tree below.

3.4Crossover - using the tree (this is the part P3Net rebuilt)

In one sentence: for each cluster from 3.3, try copying it from someone who has it differently - keep the copy if it didn't hurt, revert if it did.

Given the clusters from the linkage tree above, crossing one candidate with one level goes through every useful cluster, smallest first: pick a random donor from that level whose values differ from the candidate's on that cluster, copy the donor's values, and evaluate. If fitness got worse, revert. If it stayed the same or improved, keep it - ties are kept deliberately, so the search can drift sideways across a fitness plateau instead of getting stuck.

Why this matters for P3Net

This is exactly the step P3Net changes. Pure P3 assumes evaluation is cheap enough to spend on every cluster of every crossover - fine for a 500-gene bit string, deadly if “evaluation” means training a neural network. P3Net keeps the linkage tree and the smallest-first sweep completely unchanged, but replaces the real evaluation at every step with a cheap, learned estimate (δ̂F), and spends a real evaluation only once, at the end of the sweep, on the candidate that survived it. Section 6 below comes back to this.

4  See it in action

4.1The problem: what P3 actually needs to prove itself on

Section 4.2 runs P3 for real - but first you need to know on what. To see why the linkage tree is even needed, the algorithm below solves a small, deliberately deceptive problem, exactly the kind the original paper used: a genotype made of 4 independent “traps” of 4 genes each (16 genes total).

The goal within one trap is a full set of four ones, 1111. The path to that goal, though, is inverted: the more ones a given trap has - but not all four - the worse its fitness. One one is worse than zero ones; two is worse than one; three is the worst of all. Only a full set of four suddenly jumps to the very top. In other words: every single step toward 1111, unless it's a change of all four bits at once, is punished, not rewarded.

4.2The solution: P3 actually run on this problem

The same genotype from 4.1 - 16 genes grouped into 4 traps - is now being solved by a genuinely running P3, exactly as described in sections 2–3 and the pseudocode in section 5. The maximum possible fitness is 16 (each of the four traps at 1111) - the buttons below always show how far there is left to go.

The mode switch lets you compare two variants on exactly the same problem: full P3 (everything from sections 2–3: pyramid, linkage tree, crossover), and hill climbing alone - that is, FIHC from section 3.1 without the rest of the algorithm: a random restart, then improving one gene at a time until no single change helps anymore, with no help from crossover and no pyramid. The difference between these two modes is exactly what the rest of P3 actually contributes.

5  Pseudocode - what you'd actually have to write

Four procedures. Nothing else is needed to have a working P3.

procedure ITERATE-P3
    x ← random solution
    x ← HILL-CLIMB(x)                    // §3.1, until no locus improves
    if x ∉ seen then
        P[0].add(x); seen.add(x)

    i ← 0
    while i < len(pyramid) do
        x' ← CROSSOVER(x, P[i])          // §3.4, sweeps the linkage tree of Pi
        if fitness(x') > fitness(x) and x' ∉ seen then
            x ← x'
            P[i+1].add(x); seen.add(x)   // creates a new level if i+1 didn't exist yet
            i ← i + 1
        else
            break                        // stops climbing, settles at level i
procedure HILL-CLIMB(x)
    repeat
        changed ← false
        for locus in shuffle(all loci) do
            best ← x[locus]
            for value in alternatives(locus) do   // §5.a: YOU define this set
                if fitness(x with locus=value) > fitness(x with locus=best) then
                    best ← value; changed ← true
            x[locus] ← best
    until not changed
    return x
procedure BUILD-LINKAGE-TREE(Pi)
    clusters ← { {gene} for gene in genome }
    useful ← clusters
    while len(clusters) > 1 do
        Ca, Cb ← pair in clusters minimizing D(Ca, Cb, Pi.freq_table)  // §3.3, formula 1
        merged ← Ca ∪ Cb
        clusters ← clusters − {Ca, Cb} ∪ {merged}
        useful.add(merged)
        if D(Ca, Cb) == 0 then          // Ca, Cb are redundant - drop them
            useful.remove(Ca); useful.remove(Cb)
    useful.remove(cluster spanning the whole genome)   // the root is never useful for crossover
    return sort(useful, by=size, smallest_first=true)
procedure CROSSOVER(x, Pi)
    tree ← BUILD-LINKAGE-TREE(Pi)
    for C in tree do                        // od najmniejszego klastra
        d ← random solution in Pi where d differs from x on C
        before ← fitness(x)
        x[C] ← d[C]                        // copy the whole cluster at once
        if fitness(x) < before then
            x[C] ← revert                  // revert - worse is never kept
        // unchanged or improved fitness: keep it, even on a tie (drift)
    return x

That's the whole algorithm. There's no mutation procedure at all - everything that isn't hill climbing or linkage-guided crossover is a fresh random restart at the top of ITERATE-P3.

6  What you design yourself - applying P3 to a real problem

The same split you already know from an ordinary GA: the mechanism is fixed by the algorithm - you don't touch how crossover or the pyramid work. What changes every time is how your problem plugs into that mechanism.

Decision pointFixed by P3You decide, per problem
Genotype Solutions are vectors of discrete gene values, compared only by fitness, never by position. How your problem becomes that vector. P3Net: one gene per cell-graph edge, plus one gene per (discretized) training hyperparameter.
Allowed alternatives per locus The hill climber will try every alternative value at a given locus and keep the first improvement. What that set of alternatives actually is. Binary is {0,1}; a categorical edge might be {conv3×3, skip, none}; a continuous hyperparameter must first be discretized into a finite set.
Fitness / evaluation Higher is compared as strictly better; ties are treated as neutral and kept. What “evaluating a solution” means, and - critically - how expensive one evaluation is. That single number decides whether pure P3 is usable as-is.
Invalid genotypes Not addressed - the original bit-string benchmarks have no invalid strings. Whether some gene combinations don't correspond to a usable solution at all, and what happens to them before they reach the hill climber or crossover.
Multiple objectives Improvement is a single, strict > comparison. If you have more than one objective (accuracy and cost, say), you must define what “improved” means - usually Pareto non-domination - before hill climbing or crossover can use it.
The one decision that actually breaks pure P3

Crossover (§3.4) spends one real evaluation per cluster in a sweep - for a genome with dozens of linkage clusters, one crossover event against one level can cost dozens of evaluations. That's free on a bit-string benchmark. Not remotely free when one evaluation means training a neural network for hours.

This gap is the actual reason P3Net exists. It keeps everything in the left column of the table above completely unchanged - the same pyramid, the same hill-climbing idea, the same linkage tree, the same smallest-first sweep - and attacks exactly one thing: it replaces the real evaluation inside every cluster copy with a cheap, learned relative predictor (δ̂F(x,x′) ≈ f₁(x) − f₁(x′)) trained on solutions already fully evaluated, and spends a real evaluation only once, on the candidate that survives the whole sweep. A bounded chain depth (κ) limits how many surrogate-only steps can stack up before that real evaluation is forced, so the estimate can't drift arbitrarily far from the truth it approximates.

In other words: everything under “Fixed by P3” is what you get for free by choosing this algorithm. Everything under “You decide” is what no paper will do for you - including, for a genuinely expensive evaluation function, deciding what to do about the assumption that a real evaluation is cheap enough to spend one per cluster.

✓Checklist for applying P3 to a new problem

  • Define the genotype: what is one gene, and how many are there?
  • Define, for each locus, the finite set of allowed alternative values FIHC may try.
  • Define fitness as a single, strict comparison (or a non-domination rule, if there's more than one objective).
  • Decide what happens to genotypes that don't decode to a valid solution, if such genotypes exist at all.
  • Cost out one evaluation. If a crossover sweep costing dozens of evaluations per level is affordable, you're done - this is pure P3.
  • If it isn't affordable, that's a real design problem to solve - not a P3 parameter, but a new component (P3Net's answer: a relative, linkage-aware surrogate).
Source: B. W. Goldman and W. F. Punch, “Parameter-less Population Pyramid,” GECCO 2014 - §2 for every mechanism described above.
