NSGANetV2 - NSGA-Net with a cheap oracle instead of training

How NSGANetV2 actually works

The same NSGA-II loop as in NSGA-Net - non-dominated sorting, crowding distance, crossover, mutation - except nobody trains a network to score a candidate anymore. An oracle scores it instead: an accuracy predictor and/or a weight-sharing supernet, trained once, on a handful of real runs, before evolution even starts.

Laid out like a C4 diagram: context, then the big moving parts, then each one broken down in detail, then code, and finally a practical checklist.

1Context - the problem NSGANetV2 answers

In one sentence: NSGA-Net genuinely trains every candidate, every generation - NSGANetV2 takes the exact same loop and replaces training with a one-time-trained, cheap oracle.

NSGA-Net (the previous page in this series) applies classic NSGA-II directly to architecture genotypes: population, non-dominated sorting, crowding distance, crossover, mutation - and every single individual, every generation, gets a full, real training run to learn its true fitness. This is correct but expensive: cost measured in GPU hours grows linearly with population size times number of generations, with no shortcut at all.

NSGANetV2 (Lu et al., ECCV 2020) attacks exactly this cost, not the evolutionary loop itself. Before running NSGA-II, it builds a cheap oracle once, up front - a weight-sharing supernet and/or an accuracy predictor fit to a handful of genuinely trained architectures - and then runs exactly the same NSGA-II loop as NSGA-Net, except every fitness query goes to the oracle instead of a network trainer.

This page's place in the paper's ablation grid

In this paper's nine-armed ablation grid (NSGA-Net, NSGANetV2, SH-EMOA, MO-BOHB, TPE, random search - each pitted against P3Net on JAHS-Bench-201 and NAS-HPO-Bench-II), NSGANetV2 is the arm closest to P3Net in intent: both use a cheap surrogate to avoid paying the full price for every candidate. They differ, however, in which surrogate they use. NSGANetV2 relies on a global and absolute predictor - fit once, up front, predicting one candidate's fitness in isolation, with no notion of which genes are functionally linked. P3Net relies on a relative, linkage-aware surrogate - comparing a candidate against a specific donor, built from the same linkage tree that steers crossover, and retrained on the fly with every new real evaluation. Section 6 returns to this difference.

2Big picture - two phases feeding one loop

In one sentence: Phase A happens once and is expensive; Phase B repeats many times and is cheap - and the boundary between them is exactly the moment “real evaluation” becomes “oracle query.”

PhaseWhat happens
Phase A - building the oracleN architectures genuinely trained (typically tens to low hundreds, not thousands). A predictor and/or a weight-sharing supernet is fit to these (genotype, real fitness) pairs. A one-time cost, paid before evolution runs.
Phase B - NSGA-II with the oracleExactly the same loop as in NSGA-Net: population, offspring via crossover and mutation, scoring, non-dominated sorting, crowding distance, selection, repeat. The only change: “scoring” is now oracle.query(genotype), not training.

3  Components - breaking down each part

Three parts: building the oracle, the query to it, and the NSGA-II selection mechanics NSGANetV2 inherits with no change at all.

3.1Building the oracle - a one-time cost before the loop

In one sentence: genuinely train N architectures, remember the (genotype, fitness) pairs, fit a cheap model to them.

N architectures are sampled from the same search space NSGA-II will run over - randomly, or with a method that covers the space more evenly (e.g. Latin Hypercube). Each is genuinely trained, exactly as NSGA-Net would do for every one of its candidates. From these N (genotype, real fitness) pairs, the oracle is built - usually both at once in the original paper: a weight-sharing supernet (to score any sub-architecture without training it from scratch) and a lightweight accuracy predictor fit on top of those scores (to make scoring even faster than one validation pass through the supernet).

N is the only genuinely expensive number in the whole algorithm. Too small - the oracle generalizes poorly beyond the handful of points it saw. Too large - Phase A's cost starts to rival what running NSGA-Net directly would simply cost.

3.2Querying the oracle - oracle.query(genotype)

In one sentence: from Phase A to the end of the search, every “how good is this candidate?” is one cheap query to the model fit in 3.1 - never training.

The query is global and absolute: it receives one genotype, returns one predicted fitness, with no reference to any other candidate and no information about which genes of that genotype are linked. This is exactly the property section 6 contrasts with the P3Net surrogate. The second objective (parameters, FLOPs) usually needs no oracle at all - it can be computed analytically straight from the genotype, for free, just like in P3Net.

Why the oracle can be misleading exactly where it never looked

Because the oracle is fit once, to a fixed set of N samples, its accuracy isn't uniform across the search space. Close to the samples it saw, it predicts well. Far from them - it extrapolates, and error grows in a way NSGA-II inside Phase B has no way to detect, since it has access to nothing but the number the oracle returned. The live simulation in section 4 shows this directly: the same 12 genuinely scored points, the same oracle, and clearly different accuracy depending on how close a given candidate lies to any of them.

3.3NSGA-II selection - unchanged from NSGA-Net

In one sentence: non-dominated sorting, crowding distance, tournament, crossover, mutation - this part is the exact same mechanism described on the previous page in this series, about NSGA-Net.

NSGANetV2 doesn't change a single line of how NSGA-II decides who survives to the next generation. Front rank (how many candidates dominate a given individual) and crowding distance (how isolated it is in objective space among individuals of the same rank) are computed exactly as in NSGA-Net - the NSGA-Net page in the same series breaks this mechanism down in more detail. The only difference is one level down: the numbers these comparisons operate on now come from oracle.query(), not train_and_eval(). Sorting and crowding don't know - and don't need to know - where those numbers came from.

4  See it in action

NSGA-II genuinely computed in your browser - with a real oracle-building phase at the start and a visible point where real evaluation disappears from the loop.

4.1The problem: small, but with structure a global predictor can't see

The genotype below is a 5-gene vector, each valued 0–4 (e.g. the “width level” of a successive layer). Two objectives, both minimized: error (a nonlinear function of all five genes, with one deliberate “linkage trap” - genes 0 and 1 give a big bonus if they have the same value, whatever that value is) and cost (simply the sum of the genes - computable instantly, no training, exactly like parameters or FLOPs in real NAS).

This “linkage trap” in the error is deliberate: a global predictor that only saw a handful of random samples might not catch it at all, if none of the samples happened to land close enough on the 0–1 gene pair. This isn't hypothetical - it's exactly the difference section 6 returns to.

4.2The solution: Phase A, then Phase B, genuinely computed

Clicking “Step” first runs Phase A - 12 genuinely “trained” genotypes (the real-evaluation counter grows), from which the oracle is fit (a simple k-nearest-neighbor regressor in gene space - deliberately the simplest possible model, to hide nothing). Right after, Phase B begins: NSGA-II queries the oracle instead of training - the real-evaluation counter freezes, the query counter grows. 5  Pseudocode - what you'd actually have to write

Two blocks. Phase A is a separate procedure, run once. Phase B is almost exactly NSGA-Net - with one line swapped.

procedure BUILD-ORACLE(search_space, N)
    H ← ∅                                  // set of genuinely scored pairs
    for i in 1..N do
        g ← random genotype from search_space
        f1 ← train_and_eval(g)             // §3.1 - the only real cost in the whole algorithm
        H.add( (g, f1) )
    oracle ← FIT-PREDICTOR(H)               // regressor / supernet - §3.1, YOU choose the model
    return oracle, H
procedure NSGANETV2(oracle, pop_size, generations)
    P ← random population of size pop_size
    for x in P do
        x.f1 ← oracle.query(x)             // §3.2 - THIS is the whole swap relative to NSGA-Net
        x.f2 ← cost(x)                     // computed analytically, no training

    repeat generations times
        fronts ← FAST-NON-DOMINATED-SORT(P)         // §3.3 - unchanged from NSGA-Net
        for F in fronts do CROWDING-DISTANCE-ASSIGN(F)  // §3.3 - unchanged

        Q ← ∅
        while |Q| < pop_size do
            a, b ← TOURNAMENT-SELECT(P)     // by (rank, crowding) - unchanged
            child ← CROSSOVER(a, b); MUTATE(child)
            child.f1 ← oracle.query(child)  // not train_and_eval(child) - the only change
            child.f2 ← cost(child)
            Q.add(child)

        R ← P ∪ Q
        fronts ← FAST-NON-DOMINATED-SORT(R)
        for F in fronts do CROWDING-DISTANCE-ASSIGN(F)
        P ← first pop_size of R, sorted by (rank, crowding)
    return rank-0 front from P

Compare this with the NSGA-Net pseudocode from the previous page in this series: FAST-NON-DOMINATED-SORT, CROWDING-DISTANCE-ASSIGN, TOURNAMENT-SELECT, CROSSOVER, and MUTATE are identical there down to the letter. The difference comes down to the two oracle.query() calls instead of train_and_eval(), and the BUILD-ORACLE procedure, which doesn't exist in NSGA-Net at all.

6  What you design yourself - applying NSGANetV2 to a real problem

The selection mechanism is fixed by NSGA-II - you don't touch how non-dominated sorting or crowding works. What changes every time is how the oracle is built and how your problem plugs into it.

Decision pointFixed by NSGANetV2You decide, per problem
Non-domination rule A candidate dominates another if it's no worse in any objective and better in at least one - exactly as in NSGA-Net. How many objectives you have and how you define them (error, cost, inference time, memory use…) - the domination rule is fixed, but you decide what feeds into it.
Crowding distance Tie-break between candidates of the same rank, by isolation in objective space - unchanged. Nothing - this is the part you don't touch. If you want a different tie-break, it's no longer NSGA-II.
The oracle in the loop The “query the oracle instead of training” pattern is fixed - the whole NSGA-II loop is blind to it, accepting whatever number it gets. The oracle model family (regressor? a small MLP? a weight-sharing supernet?), and how many real samples N to spend fitting it in Phase A.
Evolutionary operators A tournament by (rank, crowding) as the parent-selection mechanism - unchanged. The concrete form of crossover and mutation, population size, number of generations, genotype encoding - the same decisions you'd make for plain NSGA-Net.
The blind spot this reveals for P3Net

NSGANetV2's predictor is global (one model, scoring every candidate individually, with no reference to the rest of the population) and absolute (predicting the fitness value itself, not a difference against a known point). Its accuracy is therefore only as good as how well the N samples from Phase A covered the region of space NSGA-II happens to be querying it about - and since N is fixed once, up front, before evolution has any chance to show which regions are even interesting, coverage tends to be uneven. Worse: the predictor has no idea at all which genes of the genotype are functionally linked - two genes that have to change together to mean anything (as in the live simulation above) are just as independent to it as two genes that have nothing to do with each other.

P3Net's surrogate (δ̂F) attacks both these points at once, unlike NSGANetV2's oracle. It's relative - it doesn't guess an absolute value, only the fitness difference between a specific candidate and the specific donor it's currently being compared against, so error doesn't have to accumulate across the whole space at once. And it's linkage-aware - built from the same linkage tree that steers crossover, so genes copied together are also scored together, not separately. This is a different bet about where a cheap surrogate stays trustworthy: NSGANetV2 bets that one global regression function is enough; P3Net bets that it only has to be enough locally, around the specific comparison currently being made.

✓Checklist for applying NSGANetV2 to a new problem

  • Define the genotype and search space - exactly as for NSGA-Net.
  • Choose N for Phase A: how many real training runs you can afford to burn before evolution even starts.
  • Choose the oracle model family and how to fit it (regressor, supernet, or both at once).
  • Check the oracle's accuracy empirically outside the Phase A samples - don't assume good accuracy near the samples means good accuracy everywhere.
  • Define the second objective (cost), making sure it can be computed without training.
  • If your problem has strong gene linkage that N Phase A samples are unlikely to cover evenly - that's exactly the gap P3Net's relative, linkage-aware surrogate fills.
